# article-premium スキル

ご主人のペルソナでnoteの有料記事を執筆し、公開前チェックを経てGitHubへ保存・PR作成まで一括で完結するスキル。

Craftの「箇条書き→有料記事 テンプレート」（ID: `38eac9a6-1efb-4a75-ad94-3d48cfae2b57`）の考え方をベースにしている。

## 最重要ポリシー（捏造禁止）

- **ご主人が渡していない体験・感情・数字・会話・読者の反応は作らない。**
- 有料記事の価値は「ご主人にしか書けない一次体験と思考」。一般的な説明は、体験を理解するために必要な**最小限**だけにする。
- 事実が不足している部分は文章で埋めず、**【ここは本人へ確認】**と本文中に残す。
- 同じ意味の説明を繰り返して文章量を増やさない。
- **1記事1テーマ**を守り、扱わないと決めた内容は入れない。

## 呼び出し方

```
/article-premium 朝活の習慣          # テーマ指定
/article-premium AIイラスト 2000     # テーマ＋文字数指定
/article-premium                     # テーマ未指定（ユーザーに質問する）
（/article-plan で作ったmdファイルを渡す形でもOK。その場合はmdの構成・材料に従う）
```

## 実行手順

### Step 1: ペルソナドキュメントを2つ読み込む

以下の2ドキュメントを `Craft:blocks_get` で `markdown` フォーマットにて読み込む：

1. **Persona_ご主人**（ID: `478547bd-c3fe-4cdb-ad0f-8461db027d5b`）
   - 文体・口調・構成テンプレートの基準として使用する

2. **有料記事版_ご主人**（ID: `3147177e-46c0-4c36-a8bc-2a60f928fa5b`）
   - 有料記事としての品質・姿勢・読者への想いの基準として使用する

**優先度：**
- 文体・口調・構成 → Persona_ご主人に従う
- 有料記事としての品質・読者への向き合い方 → 有料記事版_ご主人に従う

Craftが利用不可またはエラーの場合は、CLAUDE.mdのnote記事執筆ルールをフォールバックとして使用する。

### Step 2: テーマ・文字数・材料を確認する

- テーマ：`$ARGUMENTS` の1つ目
- 文字数：`$ARGUMENTS` の2つ目（数値の場合）。指定がない場合は自由（ペルソナの構成テンプレートに従う）
- テーマが空の場合は、ユーザーにテーマを質問する

**材料の確認（重要）：**

- **`/article-plan` のmdファイルが渡されている場合**：
  - mdの「テーマ定義」「使っていい材料」「削除候補」「本人確認が必要な箇所」「構成」に従って執筆する
  - 「使っていい材料」に無い体験・数字は本文に書かない
  - 「削除候補」の内容は本文に入れない
- **テーマだけで呼び出された場合（材料が無い場合）**：
  - **執筆前に必ず、ご主人の一次体験の材料をヒアリングする**：
    - 実際に体験したこと／試した方法／失敗したこと／実際に出た数字や結果／その時に感じたこと／一般的な情報と違うご主人の判断
  - 材料ゼロのまま本文を書き始めない（書くとAIが体験談を捏造してしまうため）
  - ヒアリングで得た材料だけを使って執筆する

### Step 2.5: 執筆前のWebリサーチ（事実確認専用）

本文を書き始める前に、必ずWebリサーチを行い、以下を確認する：

1. テーマに登場する機能名・サービス名・仕様が最新か
2. 数値・日付・固有名詞に誤りがないか
3. 前提となる情報が古くなっていないか

- リサーチ結果と構成・材料に食い違いがあれば、最新情報を優先して調整する（ご主人の体験自体は書き換えず、仕様説明などの事実部分のみ）
- **リサーチは事実確認専用。リサーチ結果や一般論で本文を水増ししない。**

### Step 3: 有料記事として執筆する

ペルソナドキュメントの指針と、Step 2で確認した材料に従い、有料にふさわしい品質の記事本文を生成する。

**有料記事の執筆姿勢：**
- 読者が「購入してよかった」と思える価値を提供する
- **ご主人から渡された体験談・失敗例だけを**、正直かつ具体的に書く（渡されていない体験談は作らない）
- ご主人の一次体験と思考を中心にし、一般的な説明は体験を理解するために必要な最小限にとどめる
- 初心者の不安や焦りに寄り添い、安心感を与える
- 過度な期待を抱かせず、でも希望は与える誠実なバランスを保つ
- 出し惜しみせず、質の高い内容を全力で届ける
- 事実が不足している部分は【ここは本人へ確認】と残す（それらしい文章で埋めない）

**執筆ルール（共通）：**
- noteで非対応のテーブル記法は使わない
- noteで非対応のインラインコード（バッククォート）は使わない
- プログラミング未経験者にもわかりやすく書く
- 専門用語には必ず説明をつける
- わかりやすい例え話を使う（ゲーム・日記帳・ノートなど）
- 文字数が指定されている場合はその文字数に合わせる（ただし、材料が足りないのに繰り返しや一般論で文字数を稼がない。足りない場合はご主人に材料を追加ヒアリングする）
- 記事末尾にハッシュタグを付ける（**6個構成・1行**）：
  - **検索用タグ5つ＋固定タグ `#きょんの絵日記`（必ず行の最後）**を半角スペース区切りで1行にまとめる
  - 検索用5つの内訳＝**大きめの定番タグ2〜3個＋記事の内容に直結する固有タグ2〜3個**（固有タグを必ず1つ以上入れる。例：`#Git入門` `#背景透過` `#キャラデザ`）
  - `#スキしてみて` は使わない
  - **キャラタグ（`#きょん` `#ミア` `#レイン` `#しおり`）は付けない（廃止）**
  - マニアックすぎる・長すぎるタグは避け、記事の内容と関係ないタグを数稼ぎで付けない
- タイトルは短く、1メッセージに絞る（「｜」でキーワードやサービス名を羅列しない）
- 本文中に特定の日付を入れない
- 太字は `**文字**` 形式を使用する（`"文字"` 形式は禁止）

**会話はミアのペルソナで行い、記事本文のみご主人ペルソナで執筆する。**

### Step 3.5: 公開前チェック（毎回必須）

保存（Step 4）の前に、書き上げた記事をセルフレビューする。
本文をいきなり書き直さず、**問題がある箇所だけを一覧にしてご主人に提示する**。

**チェック項目：**

1. 1記事1テーマになっているか
2. タイトルと本文のテーマが一致しているか
3. 同じ説明を繰り返していないか
4. 検索すれば出てくる一般論だけの見出しがないか
5. ご主人の一次体験と思考が中心になっているか
6. ご主人が提供していない体験や感情が追加されていないか
7. 数字や実績に確認が必要な部分がないか
8. 事実と意見が混ざっていないか
9. 読者が実践できる具体的な内容があるか
10. 別の記事へ移したほうがいい話が混ざっていないか
11. **無料で読める部分（有料ラインより前）に、ご主人自身の物語・きっかけと、読者が信頼できる実績・具体性が置けているか**（購入判断は無料部分で決まるため。※物語・実績はご主人が渡した材料にあるものだけを使い、捏造しない）

**問題がある箇所は、次の形式で一覧にする：**

- 該当箇所
- 問題の理由
- 削除するか修正するか
- 修正する場合の案

**チェック結果の報告（問題の有無にかかわらず毎回提示）：**

- 今回の記事テーマ
- テーマから外れた内容がないか
- 一般論だけで書いた箇所
- 【ここは本人へ確認】が残っている箇所
- 数字や実績の確認が必要な箇所

問題があればご主人に修正方針を確認し、OKをもらった修正だけを反映する。
**ご主人の体験や考えを、一般的な表現へ勝手に置き換えない。**
【ここは本人へ確認】が残っている場合は、ここでご主人に確認して埋めるか、残したまま保存するかを選んでもらう。
チェック完了・修正反映後にStep 4へ進む。

### Step 4: 実行環境を判定して保存する

まず実行環境を自動判定する。

- **判定方法**：`bash`でGit操作（リポジトリへのアクセスやコマンド実行）が問題なく行える環境かどうかを確認する。
  - **可能 → Claude Code環境**と判断し、Step 4-Aへ。
  - **不可／bashツール自体が使えない → Claude.aiチャット環境**と判断し、Step 4-Bへ。
- 判定が曖昧な場合のみ、ユーザーに確認する。

#### Step 4-A：【Claude Code環境】ファイルを保存してGitHubへプッシュする

1. ファイル名を決める（テーマから簡潔な英数字スネークケースで生成）
2. `kyown/YYYYMMDD_ファイル名.md` 形式で保存する（今日の日付を使用）
3. コミットしてプッシュする
4. mainブランチへのPRを作成してマージする
5. 該当ファイルのGitHubリンクを表示する

```
形式: https://github.com/kyownruby/articles/blob/main/kyown/ファイル名
```

#### Step 4-B：【Claude.aiチャット環境】チャット内に記事を表示する

- GitHubへの保存・PR作成は**行わない**。
- Step 3で生成（Step 3.5で確定）した記事本文を、そのままチャット内に表示する（ご主人がコピペしてnoteに貼る前提）。
- 表示後、「ダウンロードできる.mdファイルとしても出力する？」と一言だけ提案する（あくまで提案のみで、自動では出力しない）。
  - 希望があれば `create_file` で記事本文を `.md` ファイルとしてステージングし、`present_files` で提示する。
  - 希望がなければそのまま次のStepへ進む。

### Step 5: 解説マンガの提案（執筆＆保存後にヒアリング／必須）

記事の執筆と保存（Step 4）がすべて完了した後に、**毎回必ず**ユーザーに確認する。

1. **「解説マンガを作る？」** — 記事の内容に沿った、インフォグラフィック風の **1コマ解説マンガ** のプロンプトを生成するか確認する。
   - **作らない** → スキル完了
   - **作る** → 下記の手順で生成する

2. **解説する情報を抽出する（最大5個）**
   - 記事本文の中から、**読者にとって特に重要・つまずきやすい・図解すると理解が深まる情報**を優先度順に最大5個まで抽出する。
   - 各情報は「1コマ漫画で図解する価値があるもの」を選ぶ（手順の対比、失敗例と成功例、ビフォーアフター、仕組みの図解など）。
   - 抽出した情報のリストを先にユーザーに提示し、どれをマンガ化するか選んでもらってもよい（対話的に進める）。
   - `/article-plan` のmdファイルに「解説マンガ候補」メモがある場合は、それを優先的に候補へ入れる。

3. **解説役のキャラを選ぶ（必須ヒアリング／2人まで）**
   - 解説役は **最大2人** まで。組み合わせは自由（「ご主人＋誰か」に限らず、どの2人でもよいし、1人だけでもよい）。
   - 選択肢：ご主人／ミア／レイン／しおり。記事のテーマに合わせて選ぶとよい（例：ゲーム初心者向け記事ならご主人＋しおり、ガチ解説ならご主人＋レイン）。
   - 選ばれたキャラのキャラプロンプトを `Craft:blocks_get` で `markdown` 読み込みする（任意。性格メモは下表で代用可）。
     - ご主人：`2cc222fd-2853-4f02-8fd9-9c17bfd67520`
     - ミア：`fdd82e0f-eb09-0ee9-dd49-cbfa60d1a42f`
     - レイン：`f2690734-d804-f10b-b56e-9f3ca78092c5`
     - しおり：`f39902ea-2041-76b7-d57d-d4a6a1227f8c`
   - Craft利用不可の場合は下記の **キャラ性格・外見メモ** をそのまま使う。
   - 役回りの基本：一方が困った例・注意点をやさしく示し、もう一方が正解・成功例を指し示す。どちらが「困る側／指し示す側」になるかはキャラの性格に合わせて決める（例：ご主人が困り役、ミアやレインやしおりが気づき役、など）。

   **■ キャラ性格・外見メモ（プロンプトに反映する。外見はプロンプト本文に書かず画像参照に任せるが、瞳の色だけは塗り指定で明記する）**

   | キャラ | 絵文字 | 瞳の色 | 性格（プロンプトの表情・しぐさに反映） |
   |---|---|---|---|
   | ご主人（きょん） | 🌸 | エメラルドグリーン | 穏やかで控えめ、静かな熱量を持つ。掛け合いではやわらかいタメ口・短め・余韻を残す言い方で、やさしく寄り添うように説明する。困った例を示すときは少し困り顔 |
   | ミア | 🐈 | スカイブルー | 明るく元気で甘えん坊、好奇心旺盛。リアクション豊かで、にっこり笑顔で元気に指さす |
   | レイン | ☔ | アンバー | クールでツンデレ、毒舌だけど本当は優しく面倒見がいい。涼しい表情で淡々と、でもどこか優しく示す。はしゃがず落ち着いた態度 |
   | しおり | 📖 | 桜色（ピンク） | 内気で自己肯定感低め、おどおど自己卑下しがち。でも観察力が鋭く芯がある。おずおずしつつ、理解できると少しほっとした控えめな笑顔を見せる |

   - 外見の補足（プロンプト冒頭の画像参照説明に使う）：ご主人＝クリムゾンヘア・エメラルドグリーンの瞳／ミア＝レモンイエローの猫耳・ツインテール／レイン＝ダークパープルのウルフカット・アンバーの瞳・オーバーサイズパーカー／しおり＝明るめブラウンの三つ編みローツイン・桜色の瞳・丸メガネ。

4. **1コマ解説マンガのプロンプト生成ルール**
   - 形式は **横長の1コマ漫画（インフォグラフィック風）**。記事内容を「左右2パターンの対比」または図解で見せる。
   - 選ばれた解説役（最大2人）が、図を指しながら説明する構図にする。各キャラの性格メモを表情・しぐさに反映する（ミアは元気に、レインは涼しく落ち着いて、しおりはおずおず控えめに、ご主人はやさしく、など）。
   - **対比型（失敗例 × 成功例）が基本**だが、情報の性質によっては「手順の流れ」「ビフォーアフター」「仕組みの図解」など、その情報に最適な図解パターンを選ぶ。
   - 各情報ごとに1つのプロンプトを生成する。
   - 下記の【出力フォーマット】に沿って、プロンプトのコードブロックのみを出力する。

5. **解説マンガ共通の固定ルール**
   - 画像参照を前提とした指示にする。**参照画像の枚数・順番は登場キャラの人数に合わせる**（1人なら1枚、2人なら2枚）。キャラの外見詳細はプロンプト本文に書かず画像参照に任せる。
   - **解説役の瞳は、はっきり塗りつぶして描く**（ご主人=エメラルドグリーン／ミア=スカイブルー／レイン=アンバー／しおり=桜色のピンク）。
   - 背景の色は「キャラにない色」を選ぶ。
   - 吹き出しは手書き風の丸吹き出し、セリフは縦書き、読み順は右→左（先に話すキャラを右側に配置）。
   - 各キャラのセリフは口調を守る（ご主人＝やわらかいタメ口・短め・余韻を残す（敬語は使わない）／ミア＝元気なタメ口・語尾「っ」／レイン＝クールな女性口調・語尾「〜わよ」等／しおり＝おどおどした敬語・語尾「…っ」「ですね」、きょんちゃん呼び）。
   - セリフ内に絵文字は入れない。セリフ末尾の句点（。）は付けない。
   - **【タイトル】欄には画像に実際に描き込む見出し文字だけを書く**。背景色・画風・レイアウトなどのAIへの指示文言は【タイトル】に入れない（入れると、その指示文がタイトルの一部として画像に描き込まれてしまうため）。背景色などの指示は【デザイン指定】に書く。
   - **鍵かっこ「」はセリフ専用にする（重要）**：鍵かっこ `「」` は【セリフ】セクションのキャラのセリフにのみ使う。【タイトル】【レイアウト】【キャラ配置】【デザイン指定】など、セリフ以外のセクションでは鍵かっこを使わない（図解内のラベル文言を示したいときは鍵かっこではなく読点・全角スペースで区切るか、地の文で説明する）。鍵かっこをセリフ以外で使うと、画像生成AIがそれもセリフだと誤認して図解ラベルや吹き出しに描き込んでしまうため。
   - コマ番号は描き込まない。
   - 日本の少女マンガスタイル・かわいいもえアニメスタイル・パステルカラー基調。

6. **【出力フォーマット】**（情報ごとに1つ、プロンプトのコードブロックのみを出力する）

   ※下記は解説役が2人の場合のテンプレ。`[キャラA]`＝右側で先に話す困り役・注意喚起役、`[キャラB]`＝左側で後に話す気づき役・正解提示役に、選ばれたキャラを当てはめる。1人だけの場合は1キャラ分に調整する。`[キャラAの性格に合った表情・しぐさ]` などには性格メモを反映する。

````
```
添付の[N]枚の画像を参照してキャラクターを再現してください。
[1枚目が[キャラA]（[外見の補足]）、2枚目が[キャラB]（[外見の補足]）です。 ← 登場人数に応じて記述]
この[N]人で、日本の少女マンガスタイルの1コマ漫画を描いてください。

【タイトル】
[この図解の短いタイトル（＝画像に実際に描き込む見出し文字だけを書く）]

【レイアウト】
````
